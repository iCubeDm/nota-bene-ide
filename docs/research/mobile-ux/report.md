# Make the fragment, not the bubble, primary

The Nota Bene Android app already matches or beats the category on several hard things: the full command in the permission sheet, Telegram-style hold/lock/cancel voice recording, a pending-comment review pane, and an 840 dp three-pane threshold equal to Android's "expanded" class. Its core interaction model points the wrong way, though. Text selection, the thing that makes an agent reply actionable, sits two steps behind a long-press menu that targets the whole message. Research supports the two device-testing findings: selection should be the default, and fragment actions (comment, quote, label) should be the primary way to answer an agent, with the whole-message menu secondary. Telegram is the only major app with a primary-sourced fragment quote. ChatGPT, Claude and Gemini users keep asking for it on mobile, and no product splits one AI answer into separately actionable messages.

Other large gaps against current coding-agent companions: no notifications for "needs approval" or "turn finished"; server errors dropped silently; a pairing fingerprint step that cannot reject a mismatch; pane swiping that competes with code blocks, selection handles and system back; accessibility that is default Material (two `Semantics` widgets in the app). Main implementation risk: Flutter `SelectionArea` inside a reversed lazy list and a `PageView` has a stream of fixed and open bugs, so prove the direction on a device before committing.

## Fragment actions win because no one has made the bubble work

**Messaging apps put whole-message actions behind long-press and make partial selection a second step.** Telegram: tap a message (hold on iOS), then hold and drag to select; the toolbar adds "Quote", the quote shows above the composer, and tapping it later jumps with animation to the exact place ([Telegram](https://telegram.org/blog/reply-revolution)). WhatsApp has partial selection on iOS; on Android it was beta in mid 2025, shipping unconfirmed ([WABetaInfo](https://wabetainfo.com/whatsapp-beta-for-android-2-25-18-3-whats-new/)). Reading apps make the text itself selectable and turn selection into a highlight or note: Readwise Reader offers one-step "auto-highlighting" ([Readwise](https://docs.readwise.io/reader/docs/faqs/highlights-tags-notes)); Hypothesis offers Annotate or Highlight from one selection ([Hypothesis](https://web.hypothes.is/help/annotation-basics/)).

**AI chat is where the messaging model fails.** Claude app users report copy takes the whole message and selective copy is impossible; a Remote Control session (Nota Bene's product class) copies selected text wrongly ([75155](https://claudeissues.com/issue/75155-feature-request-selective-text-copy-within-messages-mobile-app-desktop-not-only), [71718](https://claudeissues.com/issue/71718-bug-cannot-copy-text-correctly-from-code-tab-remote-control-session-on-mobile-ap)). On iPad, selecting in a long remote session scrolls to the top and deselects ([72190](https://claudeissues.com/issue/72190-ipados-app-selecting-text-in-a-long-remote-macos-session-auto-scrolls-to-top-and)). OpenAI's forum has many 2026 requests for highlight-to-ask, quote-reply and anchored annotations, answered without a timeline ([highlight-to-ask](https://community.openai.com/t/feature-request-highlight-text-in-responses-to-ask-follow-up-questions-in-a-pop-up-box/1388090), [quote-reply](https://community.openai.com/t/feature-suggestion-quote-reply-to-specific-text-segments/1378659), [anchored](https://community.openai.com/t/feature-request-inline-anchored-annotations-and-contextual-threads-for-chatgpt-responses/1390620)). One says users "may need to copy and paste the text or explain which section they mean." Agent replies are long and multi-topic, so replying to the whole bubble pushes that disambiguation onto the user: the device-testing finding, stated by a competitor's users.

**Nota Bene today follows the messaging model, clumsier.** Long press on a final message opens an overlay with Comment, Select text, Copy, Reply (`mobile/app/lib/chat/message_menu.dart:229-277`). "Select text" swaps in a `SelectionArea`, selects all, and re-selects the pressed word by replaying synthetic pointer events with a long-press timer and up to 30 retry frames (`message_selection.dart:80-113`). The selection toolbar has Comment, Copy, Select all, no Reply/Quote (`message_selection.dart:172-231`). Reply exists only for the whole message and inserts a Markdown blockquote of all of it (`message_menu.dart:40-42`). Code and diff screens put Comment in the top bar, disabled until selection, with no hint (`code_screen.dart:343-349`, `files/diff_screen.dart:291-295`). One action lives in three places.

### Option A (split answers into units) vs option B (fragment actions primary)

| Criterion | A: split long answer into actionable units | B: default selection, fragment actions primary |
|---|---|---|
| Precedent | None: **no app splits one AI answer into separate messages**; no study compares chunked vs monolithic. Nearest: Perplexity's layered answer, only from teardowns ([925 Studios](https://www.925studios.co/blog/perplexity-design-breakdown)) | Telegram select-then-Quote with jump-back; reading apps' select-then-note |
| Demand | Indirect: NN/g chatbot study (8 participants, secondary write-ups only) found users get lost scrolling long replies ([Experientia](https://blog.experientia.com/?p=20115), [Nielsen](https://jakobnielsenphd.substack.com/p/ux-news-20230925)) | Direct: repeated selection/quote requests for ChatGPT, Claude, Gemini |
| Precision | Paragraph only; a comment on one identifier still needs selection | Any span down to a word; meets device finding (1) |
| Robustness | High: plain tap targets | Exposed to Flutter `SelectionArea` bugs |
| Accessibility | Good: each unit can carry a TalkBack custom action | Selection alone is not accessible: Hypothesis's selection adder failed screen-reader testing (secondary); Android asks for custom-action alternatives to gestures ([Android a11y](https://developer.android.com/guide/topics/ui/accessibility/principles)) |
| Cost and parity | Render-time splitting is cheap (each agent piece is already a list item, `chat_screen.dart:669-711`); generation-time splitting changes protocol, desktop parity and comment batch format | Replaces the synthetic-pointer code; the comment anchor (rendered text plus occurrence) already exists (`message_selection.dart:147-170`) |

**Recommendation: B, with a thin layer of A for accessibility.**
- Each final agent text piece and user message gets its own always-on `SelectionArea`. One region per item is lower risk than one over the list, because cross-list selection is where crashes cluster.
- Long press on a word starts platform selection. The toolbar (`contextMenuBuilder` + `AdaptiveTextSelectionToolbar.buttonItems`, [docs](https://api.flutter.dev/flutter/material/SelectionArea/contextMenuBuilder.html)) keeps system items and appends Comment, Quote and a labels entry.
- Quote places a removable chip above the composer. Tapping the chip, a pending comment or a sent quote scrolls to the passage and flashes it. This repairs the fragile scroll-to-message routine (`chat_screen.dart:122-161`), which can fail silently with no highlight.
- Whole-message menu moves to an explicit affordance: a "more" button on the last piece of an agent turn, or long press on bubble chrome outside text. It keeps whole-message labels, Copy all, Reply. No source documents a chat app with this hybrid, so it is a hypothesis to test.
- From A keep only the cheap part: every paragraph/block of a final reply exposes "Comment on this paragraph" and "Quote paragraph" as semantics custom actions, giving screen-reader and switch users a non-selection route without a second visible system.
- Do not split answers at generation time.

**Main risk.** Flutter selection is opt-in per subtree ([SelectableRegion](https://api.flutter.dev/flutter/widgets/SelectableRegion-class.html)) and this combination has a bug history: crash when a selectable holding a selection edge is removed while scrolled out, opened 6 Nov 2026, still open in 3.47 ([#196102](https://github.com/flutter/flutter/issues/196102)); "Select all" in `ListView` null-check error ([#124078](https://github.com/flutter/flutter/issues/124078)); scroll cleared selection until mid 2023 ([#120892](https://github.com/flutter/flutter/issues/120892)); scroll jank in `ListView`/`PageView` fixed 2024 ([#152420](https://github.com/flutter/flutter/issues/152420)). The feed is a reversed `ListView.builder` whose streaming item grows in place (`chat_screen.dart:183-196`), inside a `PageView` that turns pages on any horizontal drag (`panes.dart:220-306`). The only documented horizontal-drag rule in a `PageView` covers iOS `TextField`, not selection handles ([PR 147341](https://www.github.com/flutter/flutter/pull/147341)), so whether a handle drag loses to a page turn must be tested. Mitigation already exists in code: while recording, the pager uses `NeverScrollableScrollPhysics` (`panes.dart:233-239`). Apply the same lock while a selection is active, and keep streaming text unselectable until final (already not commentable, `comments/chat_anchor.dart:14-24`).

**What would change the recommendation.** Switch to A as primary (visible per-paragraph Comment/Quote targets, selection only in a focused full-screen reader) if: on-device tests show lost selections, crashes or page turns stealing handle drags at a noticeable rate; pending-comment quotes mostly cover whole paragraphs; or TalkBack users become a primary audience. Opposite signal (paragraph layer and custom actions unused) would remove the paragraph layer.

## Coding-agent companions set a supervision baseline the app partly misses

**By late 2026 every major coding agent has a phone surface on one loop**: session list, streaming chat, push on finish or needed input, approve/deny, steering by follow-up. Claude Remote Control keeps execution local, pairs by QR, reconnects after sleep, pushes on completion or decision ([docs](https://code.claude.com/docs/en/mobile)). Codex in the ChatGPT app pairs by QR, carries the host's Ed25519 key in the code, uses an E2E-encrypted relay (third-party analysis only: [analysis](https://codex.danielvaughan.com/2026/05/15/codex-mobile-chatgpt-app-relay-architecture-remote-agent-control/)). Cursor's iOS app has an all-agents inbox, push on turn end, Live Activities, and deliberately no editor, terminal or file browser ([Cursor](https://cursor.com/docs/cloud-agents/mobile)). GitHub Mobile added live progress notifications for agent sessions in 2026 ([changelog](https://github.blog/changelog/2026-02-26-github-mobile-track-coding-agent-progress-in-real-time-with-live-notifications)).

**Biggest omission: notifications.** None, local or push. Connections pause 10 minutes after the app is hidden (`home.dart:228-236`) and the phone UX spec lists push as a non-goal, so a pending approval blocks the agent until someone opens the app. Android guidance: one channel per event class with user-controlled importance ([channels](https://developer.android.com/develop/ui/views/notifications/channels)); at most three actions, private lock-screen visibility, cancel stale notifications resolved elsewhere ([design](https://developer.android.com/design/ui/mobile/guides/home-screen/notifications)); Android 16 Live Updates exclude chat but allow ongoing user-initiated progress ([Live Updates](https://developer.android.com/develop/ui/views/notifications/live-update)); a `dataSync` foreground service is capped at 6 h per 24 ([FGS timeout](https://developer.android.com/develop/background-work/services/fgs/timeout)), so a held socket cannot replace push. Claude users ask for Approve/Deny inside the push ([62458](https://claudeissues.com/issue/62458-feature-request-actionable-approve-deny-on-mobile-push-for-permission-prompts)). Slack's multi-device rule: hold the phone push while the user is active on desktop, with a configurable delay ([Slack](https://slack.com/help/articles/201355156-Configure-your-notifications)). Unsettled: whether push can run through a self-hosted relay without Google services. That is the first technical question.

**The permission sheet is right where the leader is wrong, and wrong where it interrupts.** Claude iOS Remote Control reportedly shows only ~100 characters of a command ([37235](https://claudeissues.com/issue/37235-feature-remote-control-allow-expanding-permission-prompts-on-ios-to-see-the-full)). Nota Bene shows the whole command in a selectable box (`permission_sheet.dart:126-192`); keep that. But the sheet auto-opens over typing or selecting, and offers only Deny/Allow while "for this session" choices exist only in the feed card (`permission_sheet.dart:67-123`).

**Code and diff viewing need two GitHub basics and one newer idea.** GitHub Mobile added a line-wrap toggle (top community request), "Jump To" file, and long-press multi-line selection for comments ([GitHub](https://github.blog/news-insights/product-news/even-better-code-review-in-github-for-mobile/)); in 2024 monospace follows the system font ([changelog](https://github.blog/changelog/2024-07-08-whats-new-in-mobile-june-update)). Linear's "guided reviews" put a summary first, go section by section, and sync viewed state between phone and desktop ([Linear](https://linear.app/now/mobile-diffs)). Nota Bene's code screen never wraps, and sizes rows from a `TextPainter` without the system text scaler behind a fixed `itemExtent` (`code_screen.dart:227-250`), so large-font users plausibly get clipped rows (not verified on device). Pinch scale is neither persisted nor tied to system font (`ui/pinch_scale.dart:19-20`). The diff view has no file jump or viewed state. Unified diff on phones, which the app does, matches every source.

## Navigation, input and states break platform rules in specific places

**Pane swiping contradicts Material's caution.** Tabs may switch by content swipe but not with content that also swipes ([M1](https://m1.material.io:443/components/tabs.html), [M2](https://m2.material.io/go/design-tabs); M3 text could not be retrieved). Swipeable views must stay clear of system gesture insets used by edge back ([edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge)). The pager takes over once an inner scroller hits its edge: code blocks (`chat/code.dart:221-223`), display math, voice waveform. Files pane tabs are tap-only (`files/files_pane.dart:130-134`). Default selection adds handles to the conflict. Keep pill tabs as the primary switch; allow page swipes only from the pill strip and bubble gutters, or when no inner scroller can move; inset by `MediaQuery.systemGestureInsets`.

**Back behaves two ways.** Header back leaves the chat from any pane (`chat_header.dart:149`); system back goes pane by pane (`panes.dart:168-178`). Play requires API 36 from 31 Aug 2026 ([Play](https://developer.android.com/google/play/requirements/target-sdk)), which makes predictive back default and intercepting back suppresses its animation ([Android 16](https://developer.android.com/about/versions/16/behavior-changes-16), [Flutter](https://docs.flutter.dev/platform-integration/android/predictive-back.md)). The header button should follow the same `PopScope` chain.

**Wide layout: right number, wrong test.** 840 dp (`panes.dart:75`) is the official start of "expanded", but landscape phones are almost all under 480 dp tall and two panes are impractical at compact height ([window size classes](https://developer.android.com/develop/ui/compose/layouts/adaptive/use-window-size-classes)). At 840 dp the chat pane is ~380 dp, narrower than a phone chat. Choose panes by width and height; let side panes collapse.

**Input loses work best practice keeps.** Telegram keeps drafts server-side, syncs them to all devices, clears them on send ([drafts](https://core.telegram.org/api/drafts)); its scheduled queue stays editable until dispatch ([scheduled](https://core.telegram.org/api/scheduled-messages)). Nota Bene drops the draft on leaving the chat (`chat_route.dart:58,97`), asks "now or after" on every busy send without remembering (`send_now.dart:11-32`), and never shows a queued message as queued. Voice: WhatsApp set the standard with preview, pause, waveform, 1.5x/2x ([WhatsApp](https://blog.whatsapp.com/making-voice-messages-better)); ChatGPT drew complaints when dictation stopped showing an editable transcript before sending ([forum](https://community.openai.com/t/voice-dictation-no-longer-shows-transcribed-text-before-sending-major-usability-regression/1177339)), which matters more for coding where a mis-heard identifier is costly. The app's hold-release sends at once; playback has no speed control (`voice/voice_view.dart:83-88`). Ahead of baseline: the outbox lets a voice send outlive the chat (`chat/window_tab.dart:99-103`), and TalkBack has a tap path into locked recording (`voice/record_button.dart:212-220`).

**States follow NN/g on paper but not in recovery.** NN/g: indicator after ~1 s; for long waits step labels, estimate, cancel ([progress](https://www.nngroup.com/articles/progress-indicators/)); errors near source with next step and input kept ([errors](https://www.nngroup.com/articles/error-message-guidelines/)). Material: persistent offline indicator plus Retry snackbar ([offline](https://m2.material.io/design/communication/offline-states.html)). Nota Bene's "Working..." has no phase, elapsed time or Stop (`chat_screen.dart:206-215`). Stop is a red 40 dp button 6 dp from Send, no confirmation (`composer.dart:349-366`). No snackbar has an action (`composer.dart:79-127`). Server errors go to a stream nothing listens to (`window_tab.dart:156,171,323-324`): the most basic error rule broken, tell the user.

**Pairing shows fingerprints, then trusts anyway.** Signal and Tailscale document QR linking with expiry, explicit approval and device lists ([Signal](https://signal.org/blog/a-synchronized-start-for-linked-devices/), [Tailscale](https://tailscale.com/kb/1336/device-add-qr-code)). Nota Bene's confirm screen shows both fingerprints but offers only Done, and the host is already stored (`pairing/confirm_screen.dart:31-52`), so the comparison is decorative. No primary source for a specific fingerprint UX, but the minimum is obvious: "They match" / "They differ", nothing stored until match.

## Accessibility is default Material plus two hand-written nodes

Android asks for labelled long-press actions, merged semantics per group (a bubble), headings, unique pane titles, custom actions for gesture-only interactions, cues beyond colour ([Android a11y](https://developer.android.com/guide/topics/ui/accessibility/principles)). In Flutter, changing content uses `Semantics(liveRegion: true)`; `SemanticsService.announce` is deprecated on Android (flushes TalkBack's queue) ([announce](https://api.flutter.dev/flutter/semantics/SemanticsService/announce.html), [liveRegion](https://api.flutter.dev/flutter/semantics/SemanticsProperties/liveRegion.html)). Android 14 scales fonts non-linearly to 200%; test at max ([Flutter](https://docs.flutter.dev/release/breaking-changes/android-14-nonlinear-text-scaling-migration)). TalkBack has its own selection gestures; since 13.1 actions are reached via reading controls ([gestures](https://support.google.com/accessibility/android/answer/6151827)).

The app has `Semantics` in two places (`chat_header.dart:214`, `record_button.dart:212`) and no `liveRegion`, `MergeSemantics` or sort key. Several targets are under 48 dp (sourced only secondarily): 18 dp comment badges (`files/file_markdown.dart:151-155`), 24 dp draft remove, 32 dp quick labels. Labels are 10.5-11 px (`window_sheet.dart:430`). The header is clamped at 1.3x (`chat_header.dart:59-61`). The fragment redesign makes this urgent: a selection-based model is inaccessible unless each commentable unit also exposes custom actions.

## Where the notes disagree or stand on thin ground

The sharpest contradiction: the selection note infers default-selectable text "matches the reading-app model"; the chat-apps note infers "a design that does not rely on native OS text selection (explicit per-paragraph targets) avoids a known pain point." The recommendation settles it as B plus a paragraph custom-action layer, with stated flip conditions. Telegram, the fragment-quote champion, does not make selection default either (reached via a tap-opened message view): precedent supports fragment actions, not default selection, which rests on reading apps and complaints.

Load-bearing sources that are secondary or unopened: all Claude evidence (claudeissues.com aggregator pages not opened); NN/g chatbot findings (summaries of an 8-participant study); Perplexity structure (teardowns); Gemini "Select text"/"Ask Gemini" (unfetchable Android Authority, APK teardown); WhatsApp Android partial selection (may not have shipped); Codex relay (third-party, launch details differ); GitHub long-press multi-line comments (2020-2021 sources only). Material guidance is M1/M2 throughout since m3.material.io renders client-side (tab swiping, selection toolbar, offline states). The 48 dp target, contrast ratios and M3 type scale are unsourced in the notes. Flutter has no first-party Material 3 Expressive, so the floating pill header and tabs are custom either way ([#168813](https://github.com/flutter/flutter/issues/168813)). Unresolved evidence conflicts: skeleton screens (one study slowest, another fastest; [summary](https://theplusaddons.com/blog/skeleton-loading-screen/)); progress-indicator threshold (1 s NN/g vs over 10 s [UX Tigers](https://www.uxtigers.com/post/progress-indicators)). No evidence at all on jump-to-bottom, new-message markers, timestamps, enter-to-send or composer growth in major messengers; those recommendations rest on convention.

## Open questions for on-device testing

Selection mechanics first, since the main recommendation depends on them:
- Does a per-item `SelectionArea` in the reversed `ListView.builder` keep its selection when scrolled out and back?
- Does it crash when disposed while holding a selection edge (the #196102 class), especially while a streaming item above grows?
- Does a horizontal handle drag lose to the `PageView`, with and without the pager lock?
- Can a word be selected inside a code block, table or display math (horizontal scrollers) without a page turn or inner scroll?
- Do long press on text vs on bubble chrome stay distinguishable at real padding, so users find "more" unaided?

Then behaviour around selection:
- What share of real pending comments quote less than a paragraph? (Signal for B vs A.)
- Do TalkBack users find paragraph custom actions via the reading-controls menu?
- Does a polite live region announce "response complete" reliably on Pixel and Samsung TalkBack?
- How do pill, header and composer behave at 200% font scale, and the code viewer given the fixed `itemExtent`?
- Does the deferred permission banner get approvals answered as fast as the auto-opening sheet?
- Is Stop mis-tapped in one-handed use?
- Relay: can push with Approve/Deny reach the phone through the self-hosted relay without Google services, and with what latency under Android background limits?

## Conclusion

No phone client in this category makes fragment-level responses to an agent work well: leading AI apps get complaints, and messaging apps solved it only for short messages. Nota Bene already has the hard parts (comment anchoring, pending-comment batching, a review pane) and is one inverted interaction (selection first, message menu second) away from answering what others leave open. That makes the selection rework a differentiator, provided it survives the Flutter risks on a real device. Run that spike before the rest of the P0 work, because its result decides between the two answer models. The rest of P0 is cheaper: notifications, surfaced errors, an honest fingerprint check. These make the phone safe to trust while away from the desk, the reason a companion exists.
