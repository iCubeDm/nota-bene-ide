# Nota Bene

A browser agentic development environment (ADE) over Claude Code, Codex and omp: the chat with the agent, inline margin comments on any reply or file (sent as one batch), file tree, media viewer, sessions. Claude uses the Agent SDK; Codex uses its installed CLI app-server (0.166.0+); omp runs over ACP (`omp acp`, 18.16.0+).

## Layout

- Root: the app (React + TypeScript), npm workspaces `shared/`, `server/`, `web/`, plus `e2e/`, `bin/nota-bene.mjs` (launcher), `plugin/` (the Claude Code plugin: `plugin/skills/nb/` is the `/nb` skill, `plugin/.claude-plugin/plugin.json`) and `.claude-plugin/marketplace.json` (the marketplace that lists it).
- `docs/` — notes, specs, plans, the draft feedback to Anthropic.

The local root compat symlinks (`server.mjs`, `public`, `ide.sh`, `skill`, `.sessions.json`) were removed at the M5 switch-over on 2026-10-26; `~/.claude/skills/nb` points at `plugin/skills/nb/` (one copy serves the checkout link and the plugin). On Windows that link is a junction, which needs no admin rights or Developer Mode: `mklink /J "%USERPROFILE%\.claude\skills\nb" "<checkout>\plugin\skills\nb"` in `cmd`.

## Rebuild (root)

Node >= 23.6 (the server runs `.ts` directly). From the repo root:

For a checkout-backed command available from any project directory, install a symlink once
(run these commands from the checkout root, with dependencies installed):

```sh
mkdir -p "$HOME/.local/bin"
ln -s "$PWD/bin/nota-bene-dev.mjs" "$HOME/.local/bin/nota-bene-dev"
```

Ensure `~/.local/bin` is on `PATH`. On Windows a symlink needs Developer Mode, and a `.mjs` is not a command: put a `.cmd` shim in a folder on `PATH` instead, `nota-bene-dev.cmd` holding the one line `@node "<checkout>\bin\nota-bene-dev.mjs" %*`. `nota-bene-dev [dir] --agent codex` uses the ordinary
launcher from that checkout: it builds stale web assets, opens a browser and supervises
the server. All normal arguments work, including `--new`, `--resume`, `--fork`,
`--detach` and the discovery helpers. With no directory it opens the caller's current
directory; with no agent it offers the ordinary terminal agent picker. Ctrl-C stops a
foreground launch; use the window's Stop button after `--detach`.

State defaults to `~/.nota-bene-dev` (shared with `npm run dev`), so the installed app's
windows and preferences are separate. The command deliberately ignores inherited
`NOTA_BENE_HOME`; set `NOTA_BENE_DEV_HOME` to use another dev state directory. Native
agent login and transcript storage remain managed by each provider. The symlink follows
the checkout's current branch; it does not update code or switch branches. This dev-only
command is not shipped in the npm package. For Vite hot reload, use `npm run dev` below.

- `/nb`, `/nb new`, `/nb fork` — from Claude Code, via `plugin/skills/nb/` (linked with `ln -sfn "$PWD/plugin/skills/nb" ~/.claude/skills/nb`, or installed as the plugin): open the window for the caller's folder; resume its last session / start fresh / continue this conversation as a branch. The skill runs `node "${CLAUDE_SKILL_DIR}/open.mjs" --data '${CLAUDE_PLUGIN_DATA}' --plan` (the data path single-quoted: a live `${...}` makes Claude Code refuse the line; `allowed-tools` is `Bash(node */nb/open.mjs* *), Bash(node */bin/nota-bene.mjs* *)`) (guards, the "already open" check; it launches nothing and prints `NB-RUN` / `NB-WAIT` / `NB-NAME`), then runs the foreground launcher as a Claude Code background task (it shows in the session's task list, its output is the window's log; stopping the task, or ending the Claude Code session, stops the window), then `open.mjs --wait` (polls `--find` up to 40 s) for the URL. `open.mjs` is a plain Node script so that it runs on Windows too; it ships alone in `plugin/` (no imports beyond Node's own, no `package.json`), so it carries its own small copies of the PATHEXT lookup, the `npm-cli.js` spawn and the `taskkill` call. With no `node` at all the shell fails before the script runs. On Windows `NB-RUN` and `NB-WAIT` carry forward-slash paths (`C:/...`), which Claude Code's Bash tool (Git Bash) reads back. It finds the launcher in this order: a checkout (`bin/nota-bene.mjs` three levels above the physical skill dir, Node >= 23.6); else the npm package `nota-bene-ide@<plugin version>` under the plugin data dir (`${CLAUDE_PLUGIN_DATA}` is not in the env of Bash commands, so SKILL.md passes it as `--data`; Node >= 22). The first run installs it with `npm install --prefix <data>` inside NB-RUN (`open.mjs --run`, in the background task, never in the `--plan` preprocessing; the plan adds an `NB-NOTE:` line and `--wait` waits for the install up to 540 s, `NB_INSTALL_WAIT_SECS` for tests); one install per version in `<data>/<version>/` (about 330 MB each, not pruned yet); `.nb-installed` there (written last) tells it is done, `.nb-install-failed` makes `--wait` report a failure at once, and `--wait` also reports at once an install whose lock holds a dead pid, or that never started. Once installed, NB-RUN is plain `node <data>/<version>/node_modules/nota-bene-ide/bin/nota-bene.mjs ...`. The commands in the plan are built by `q()`: safe words as they are, anything else single-quoted (Claude Code refuses backslash-escaped spaces and `$'\320...'` escapes). The plugin version must equal the root `package.json` version (a test checks it) and `plugin/` must hold no `package.json` or lockfile (Claude Code would run its own npm install there). Test: `scripts/nb-open.test.ts` (kept out of `plugin/`, which ships to users; test-only env `NB_TEST_NODE_VERSION`, `NB_TEST_RECLAIM_GATE`). The Codex and omp skills' `open.mjs` on Windows run the `.mjs` behind npm's `nota-bene.cmd` shim with their own `node`, since Node cannot spawn a `.cmd` without a shell.
- `node bin/nota-bene.mjs [dir] [--port N] [--resume ID [--fork]] [--new] [--detach] [--no-open]` — the launcher the skill uses. It rebuilds a stale `web/dist` (at launch and before a restart), then opens the browser (`--no-open` skips that). One window per folder (a launch takes the folder's lock and gives way to a window already serving it, waiting up to 10 s for one in its restart gap). It supervises the server: exit 75 relaunches at once with `--continue`; 77 (HANDOVER) hands the window over to a newer version (see In-app update below); 0, 130, 143 exit; anything else is a crash, relaunched after 1 s, giving up at 5 crashes within 60 s. A relaunch keeps the port and the registry entry (no other launch takes the port meanwhile); a 98 on a relaunch gives up at once. `--detach` prints one line (`opened URL` or `already-open URL`, the URL with the `#t=` login fragment) and leaves the window running on its own (terminal use; its log is `$TMPDIR/nota-bene-PORT.log`). Without `--detach` it runs in the foreground: the server's `Nota Bene: URL  project: DIR` line is its first output after any build, Ctrl-C (SIGINT) or SIGTERM stops the server and unregisters the window. The server is spawned with an IPC channel and stops when it closes, which happens however the launcher ends, so a SIGKILLed launcher leaves no orphan; the channel also carries `nota-bene:stop`, the stand-in for SIGTERM on Windows (no signals there). Without a channel (an older launcher) the server falls back to watching its parent (`NOTA_BENE_LAUNCHER_PID` vs `process.ppid` and `pidAlive`, every 2 s). An inner (handover) launcher watches its outer part through IPC too. A foreground launcher stops (as on SIGTERM) when its parent shell is gone (ppid and `pidAlive`; not a `--detach` child, nor one started with ppid 1). On Windows a launcher never forwards signals: its children get the stop message and, after 5 s, `killTree`; exit `0xC000013A` (Ctrl+C) counts as clean, and libuv's kill-on-close job makes a node process's non-detached children die with it. The browser opens through `cmd /c start "" <page>` on the mode-600 page (`NOTA_BENE_TEST_OPENER`, test-only, runs a script with node in its place).
- `node bin/nota-bene.mjs --find DIR [--scan]` prints the port of the live window serving DIR (exit 1 if none; `--scan` also asks the other ports of the range, for a window whose registry write was lost); `node bin/nota-bene.mjs --last DIR` prints DIR's last session id if its transcript still exists (exit 1 otherwise); `--url PORT` prints the window's login URL, `--front PORT` brings it to front logged in (see Access token). All are the skill's helpers.
- `npm start [-- <dir> --port N --resume ID --continue]` — builds `web/dist`, then serves app + API from the server directly, unsupervised (default port 4777; project = the directory you ran npm from, or the `<dir>` argument, relative to it).
- `npm run dev` — (login: `npm run dev:open`, see Access token) server on 4780 (`node --watch`, with `--allow-origin http://localhost:5173`) + Vite on 5173 (proxies `/info` and `/ws` to the server). Open http://localhost:5173. Dev has its own state dir, `~/.nota-bene-dev` (set `NOTA_BENE_HOME` to override), so experiments never touch the working `~/.nota-bene`; the server logs `state: <dir>` at startup.
- `npm test` — unit tests (Vitest, ports are 0 / random). All projects set a fixed default provider and clear inherited supervision flags, so a run inside a Claude or Codex window has the same baseline. Provider tests override it explicitly.
- `npm run e2e:codex` — Codex browser acceptance; run separately from `npm run e2e` because they share ports.
- `npm run e2e:omp` — omp browser acceptance on the scripted ACP agent `server/test/fixtures/acp-server.mjs`; also run separately.
- `npm run e2e` — Playwright, ports 4791-4795. The `files` project uses `ffmpeg` on PATH to generate its media fixtures at startup; without it the media tests are skipped with a message (`NB_E2E_FFMPEG=0` forces that path).

- `node scripts/build-package.mjs [--out DIR]` — builds the publishable npm package into `pkg/` (git-ignored; never publishes): esbuild bundles `server/src/main.ts` and `bin/nota-bene.mjs` to plain JS at the same depth (`server/src/main.js`, `bin/nota-bene.mjs`; `@nota-bene/shared` inlined, `ws` and the Agent SDK external), a FRESH `web/dist` (own outDir, emptied; the local `web/dist` keeps its old chunks), the two blend assets, LICENSE, README and a generated `package.json`. The name (`PACKAGE_NAME`, now `nota-bene-ide`; the command is `nota-bene`) and the Node floor live as constants in that script; the version is the root `package.json` `version` (the root stays `private`). Installed, there is no `web/src`: the launcher never builds, `/info.codeChanged` is false (no `.ts`), About reads the package version, and nothing is written next to the code (state is in `NOTA_BENE_HOME`). Test: `bin/package.test.ts`.

Experimental 3D (the model tab for `.glb` `.gltf` `.blend`, Blender): off by default, on with env `NOTA_BENE_EXPERIMENTAL_3D=1` on the server. Off: `/model` is a 404, Blender is never looked up (`/info.blender` false), `hello.capabilities.model3d` is false, and the web treats model files as any other unsupported file (text kind, generic icon) and never fetches the three chunks. The e2e `files` fixture runs with it on; the `controls` fixture keeps it off (`e2e/model3d-off.spec.ts`).

Ports: launcher windows may sit anywhere in 4777-4799 except 4780 and 4790-4795; dev 4780 (server) and 5173 (Vite); tests use only 4790-4795 (manual smoke 4790, unit/e2e 4791-4795), never another port. `/info.root` tells windows apart.

Windows (native since 1.9.0, #322): what differs from POSIX goes through two modules. `server/src/platform.ts` (the launcher imports it too): `resolveBin` (PATH × PATHEXT; a Windows app execution alias, such as a Store `pwsh`, counts), `spawnSpec` (a `.cmd`/`.bat` through `cmd.exe /d /s /c` with tested quoting), `npmSpec`/`npxSpec` (on Windows the running Node's `npm-cli.js`, no shim; macOS and Linux keep `npm` from PATH), `killTree` (`taskkill /T /F` on win32, the group elsewhere), `pidAlive`, `samePath`/`pathKey`, `realpathNative`, `renameRetry`, `HIDDEN` (`windowsHide`). `shared/src/paths.ts` (`@nota-bene/shared/paths`, web and server): `isAbsPath`, `toSlash` (the wire form `C:/Users/x`), `basename`, `dirname`, `isInside`. Rules: no bare `spawn('npm' | 'npx' | 'codex' | ...)` (resolve, then `spawnSpec`), no `process.kill(-pid)` (`killTree`), no hard-coded `/` path checks or `===` on paths (`isAbsPath`, `samePath`, `isInside`). The repo is LF on every OS (`.gitattributes`). CI tests on Ubuntu only: check Windows by hand before a release.

- **Paths on the wire.** Absolute paths the server sends (`hello.tmpDirs`, the session root, `/sessions` root and cwd, `/sources` dir and alias, `/system/windows` root) go through `server/src/wirePath.ts`: on Windows the form is forward slashes with an upper-case drive (`C:/Users/x/proj`), elsewhere unchanged. The server takes that form back; `switch.dir` takes any absolute path. Project-relative paths are always `/`-joined. `/info` and the window registry keep the native form, so compare them with `samePath`. The page (`web/src/lib/paths.ts`) reads a backslash in an agent ref (`src\a.ts`) as a separator only when the server is a Windows one; on macOS and Linux a backslash stays part of the name.
- **Agents.** `server/src/agent/bin.ts` (`agentSpawn`, `agentOutput`) is the only way to spawn an agent CLI: a `.cmd` shim runs through `cmd.exe`, a `.js` through Node, and an npm install of Codex starts its bundled `codex.exe` directly. On Windows the Codex and ACP RPC children are stopped hard as a tree (`taskkill /T /F`), with no graceful shutdown. The optional `AgentBackend.warning()` is reported once as a `server-error` with its own `where`; `where: 'git-bash'` is Claude Code without Git Bash (looked up in `CLAUDE_CODE_GIT_BASH_PATH`, beside `git` on PATH, then `Program Files\Git`).
- **Liveness and stop.** The server stops when the launcher's IPC channel closes (see the launcher above); `nota-bene:stop` on that channel is the Windows SIGTERM, and `killTree` follows after 5 s. Probe a pid with `pidAlive`, never `process.kill(pid, 0)` by hand. `killTree` on Windows is `taskkill /T /F`: never use it on a tree of MSYS processes (Git Bash and what it started), which can break MSYS's shared state so that the next `bash` on the machine dies at start with "cmalloc would have returned NULL". A Git Bash `!` run carries `NOTA_BENE_SHELL_RUN=<mark>` in its environment, and Stop kills every MSYS process with that mark from inside MSYS.
- **Named pipes.** Windows has no unix sockets, so the remote connector listens on `\\.\pipe\nota-bene-remote-<hash>` and the Whisper host on `\\.\pipe\nota-bene-whisper-<hash>-h<proto>-<pins>` (`<hash>`: 16 hex of SHA-256 of the real state base path). A pipe is not a file with a mode, so each client proves a per-home secret, made on first use with the create-once link pattern: `remote/control-secret` and `whisper-host/host-secret`. A pipe name stays held while any accepted connection to it is open. Deleting or replacing `control-secret` needs a restart of a running connector; a host secret that is not valid sends the window to its own model, told once.
- **Private files.** On Windows `stat` reports 666 and no uid, so `readPrivateFile` skips the mode and owner checks and trusts the profile's ACL; a symlink or junction is refused with `lstat` (there is no `O_NOFOLLOW`; never OR an undefined `fs.constants` flag in). `stateDir` refuses a state folder outside `%USERPROFILE%` (case-insensitive, junctions resolved) unless `NOTA_BENE_ALLOW_SHARED_HOME=1` (exactly `1`). On file systems without hard links (FAT, exFAT, some shares; every OS) the token is created with `O_EXCL`. State and project writes rename through `renameRetry` (about 2 s on Windows, for antivirus and indexers). The project-icon key (`realpathSync.native` of the root) is Windows-only.
- **`/system/prefs`** answers `shell` and `shells` (where each one is installed) on win32 only; POST takes `shell` (`auto`, `git-bash`, `pwsh`, `powershell`, `cmd`).
- **Tests.** A POSIX-only test gets `it.skipIf(process.platform === 'win32')` with the reason beside it, or a Windows variant; never weaken the POSIX assertion. A directory link fixture is a junction (`fs.symlinkSync(target, link, WIN ? 'junction' : 'dir')`), which needs no rights; a file symlink needs Developer Mode or admin, which a CI runner may lack (some `bin/nota-bene.test.ts` fixtures still use them). Full suites on one machine share ports 4791-4795 across checkouts and are serialized; a CI runner runs one suite and needs no lock. The remote relay tests need Go on PATH (the binary is `nb-relay.exe`). E2E needs Git for Windows and ffmpeg on PATH; `e2e/serve.mjs` keeps `GIT_CONFIG_GLOBAL=/dev/null` because Git for Windows refuses `\\.\nul`. `scripts/build-package.mjs` moves an old `pkg/` to the Recycle Bin through Windows PowerShell (`trash` elsewhere).

State lives in `~/.nota-bene/` (override with `NOTA_BENE_HOME`), never in the repo:

- `token` — the local access token (32 random bytes as hex, mode 600, state dir 700; see Access token below). Deleting it rotates it at the next server start. `control-token` is the separate secret of the cross-window `/control/` routes
- `open/` — the pages the launcher opens the browser on (mode 600, dir 700; each holds the login URL of one launch, which dies with that launch; same trust as `token`). Removed 30 s after by the launcher if it is still running; a page left by a launcher that exited stays until the next page is written more than 10 minutes later (the next sweep)
- `sessions.json` — the last session per project (folder)
- `archived-sessions.json` — the Sessions menu's archive: the session ids it hides, oldest first (at most 5000; `server/src/archivedSessions.ts`). Nota Bene's own, so the agent's files are never touched; an id the listing does not have is ignored. A delete drops its id. The open session stays in its folder group even when archived
- `prefs.json` — agent permission mode per project dir (`modes[root]`)
- `comments/<sessionId>.json` — pending and sent margin comments of one agent session
- `attachments/<sha256>.<ext>` — pasted images, content-addressed; only ids travel over the socket
- `update-check.json` — `{latest, at}`: the newest version seen on npm, shared by every window (the registry is asked at most once a minute)
- `runtime/` — the in-app update: `<x.y.z>/` (a full `nota-bene-ide` package each, installed by `npm install --prefix`), `current` (the version a launcher hands over to), `state.json` (`auto`, `previous`, `failed`, `rolledBack`), `update.lock` (one install at a time across windows), `update.log` (npm's output). Keeps `current`, the one before it and any version a live window runs
- `windows/<port>.json` — the window registry (`root`, `pid`, `launcherPid`, `startedAt`; `version` and `nonce` from the launcher, kept when the server re-registers after a folder switch: `version` keeps that release from being pruned)
- `locks/<hash>` — per-folder launch locks
- `history/<sessionId>.jsonl` — the archive of the conversation before each compaction, one line per segment (the SDK replays a session only from its last compaction)
- `cache/blend/<key>-<blender version>.glb` (key = sha256 of the file bytes + its root + its folder) — `.blend` files converted to GLB for the model tab (re-creatable; safe to delete)
- `trash/` — `attachments/` and `history/` subfolders: what Settings → Storage "clean" moved (never deleted)
- `usage/` — shared by every provider and project, never per window: `<provider>.jsonl` (normalized append-only records, 600), `<provider>.state.json` (byte offset and parser context per transcript), `trips.json` (reset points), `<provider>.lock` (one importing window). Deleting it loses history older than the transcripts; the rest is re-imported

## In-app update

A published window (package root without `.git`) updates itself; a checkout never does. Code: `server/src/update.ts` (the check, `update-check.json`), `runtime.ts` (the runtime store and the install), `updater.ts` (one window's part), `/system/update*` routes in `system.ts`, `web/src/shell/UpdateNotice.tsx`.

- Launcher: the outer part runs the launcher of `runtime/current` when it is a newer plain `x.y.z` than its own, as a child (the inner part), on the same port with the same nonce. The inner part runs the window and returns 77 to the outer part. Exit **77** (HANDOVER) from the server (only with `NOTA_BENE_HANDOVER=1`) or from an inner launcher means "a newer version is current: hand over"; the outer part starts that version, or its own when `current` is gone or was rolled back. The server exits 77 only in a pause (no turn, question or approval, no `!` command run, no running task of the agent: `busy` in `server.ts`; with a page open the page asks for it when its composer is idle — no draft, images, upload or unconfirmed send — or the user presses Restart, with none open the server does it); an accepted `/restart` exits only once its reply is out and checks the pause again then, so a send that came meanwhile cancels it. 77 does not count as a crash. After a 77 the page reloads itself when it reconnects to a server of another release and is idle (drafts are not kept across a reload), otherwise it offers **Reload**. A window that starts when `current` is already newer hands over at launch and shows no **Updated to** (`NOTA_BENE_UPDATED_FROM` is set only after a live 77).
- Rollback: the new version did not answer `/info` within 20 s, or its launcher exited (not cleanly, not 77) within its first 60 s: `current` goes back to the version that ran before, `state.json` records `rolledBack`, and the window runs the old one. 76 (no agent binary) is no rollback. The other handed-over windows on the rolled-back release go back in their next pause, also when `current` now names the launcher's own version, which has no `runtime/` folder. Automatic updates never retry a rolled-back release; a failed install (`state.json` `failed`) is retried an hour after it failed (`RETRY_FAILED_MS`).
- Env, set by the launcher: `NOTA_BENE_INNER=1` (the child is an inner part), `NOTA_BENE_HANDOVER_NONCE` (the nonce the outer part chose, so the inner one keeps the open tabs logged in), `NOTA_BENE_HANDOVER=1` (the server may update: a published launcher only), `NOTA_BENE_UPDATED_FROM` (the version the window was just updated from; the header shows **Updated to** once). `NOTA_BENE_NO_UPDATE_CHECK` forces the check off.
- Test-only, never set otherwise: `NOTA_BENE_TEST_PUBLISHED=1` (a checkout launcher counts as published), `NOTA_BENE_TEST_HANDOVER_INFO_MS` (shortens the 20 s `/info` wait), `NOTA_BENE_TEST_CRASH`.
- Routes (behind the key): `GET /system/update` (status: `current`, `latest`, `phase` = none | available | installing | ready | failed | rolled-back, `canUpdate`, `auto`, `busy`, `log`, `failed`, `rolledBack`, `updatedFrom`), `POST /system/update/install` (409 where the window cannot update), `/restart`, `/auto {on}`, `GET /changes`.
- Manual smoke on 4790: pack with `node scripts/build-package.mjs`, install the archive into a temp prefix, put a second archive with a higher version into `<NOTA_BENE_HOME>/runtime/<version>/` and `current`, start the first with `--no-open`, and see `/info` answer with the second version and `/system/update` show `updatedFrom`.

## Providers

Launch with `--agent claude|codex|omp` (Claude by default). Each window stays bound to
one backend. Claude state remains at the base `NOTA_BENE_HOME`; Codex and omp use
`providers/codex` and `providers/omp` under that base. Window discovery, locks, secrets, preferences,
comments and archives are isolated. The session picker only lists its provider.

Codex's native transport, event mapper, paginated history and lifecycle live in
`server/src/agent/codex/`. Keep native RPC shapes inside that adapter. Its installable
CLI/Desktop skill is `codex/skills/nb/`; it is separate from Claude's plugin skill.
The repository marketplace `.agents/plugins/marketplace.json` installs `codex/plugin.json`
and its skill. Marketplace invocations use the pinned npm runtime through `npm exec`;
standalone skills use the bundled launcher or PATH. The npm runtime and repository
plugin are separate distribution artifacts; adding marketplace metadata does not
replace an already published npm version.
See the guide's Codex section for API gaps; do not infer parity from the shared UI.

omp runs on the generic ACP adapter in `server/src/agent/acp/` (`rpc.ts`, `map.ts`,
`session.ts`, `backend.ts`); everything omp-specific is the `OMP` profile in `acp/omp.ts`.
Keep ACP frame shapes inside that folder and omp wording inside the profile. omp is
spawned as `omp --approval-mode <m> acp` (flags before `acp`), needs
`clientCapabilities.elicitation.form` (without it omp denies tool approvals) and keeps
its sessions in its default storage (never pass `--session-dir`). The omp skill is
`omp/skills/nb/`.

## Workflow

Every change reaches `main` the same way. There is no bypass, for admins either, and
force-push and deletion of `main` are refused.

1. Open a GitHub issue.
2. Branch from `main`. Commit subjects read `gh-<issue>: <message>`.
3. Open a pull request with the same kind of title and `Closes #<issue>` in its body.
4. Wait for the required checks: `test (ubuntu-latest)` and `pr-format`. The branch must be up to date with `main`.
5. Squash merge, the only method allowed. The title becomes the commit on `main`.

There are no release branches: `main` is always the next release, and a release is a
version-bump pull request into `main` plus a tag on its commit (see below). A large piece
of work is an epic issue whose subtasks are checkboxes in it, not issues of their own;
each subtask is its own pull request into `main`, titled `gh-<epic>: <message>`
with `Part of #<epic>` in its body; the last one closes the epic.

## Releasing

A release follows the workflow above, then publishes from a tag on `main`.

1. Open an issue for the release; its body is the changelog of the version.
2. Bump the version on the issue's branch. Root `package.json` is the version source.
   Keep its lockfile root entries, `plugin/.claude-plugin/plugin.json`, `codex/plugin.json`,
   the npm pin in `codex/skills/nb/SKILL.md`, the Codex and ACP client metadata (`CLIENT_VERSION` in `server/src/agent/acp/rpc.ts`), the README pins
   and the `docs/architecture.md` header in sync.
3. Move the notes under `## Unreleased` in CHANGELOG to the version's section. Update README
   and guide for user-visible changes. Keep AGENTS.md short; CLAUDE.md imports it and this
   file holds operational detail.
4. Run types and the package/skill/launcher tests. Run browser suites sequentially when
   behavior changes; a documentation/version-only release needs focused checks.
5. Merge, wait for CI on `main`, then put an annotated tag `vX.Y.Z` on that commit and push
   it by name, straight away: the plugins on `main` pin the version, so new installs fail
   until npm has it.
6. The tag starts `.github/workflows/publish.yml`. It checks that the tag matches
   `package.json` and that the commit is on `main`, builds with
   `node scripts/build-package.mjs`, publishes that archive through npm trusted publishing
   and creates the GitHub release with the archive and the version's changelog. The push
   of the tag is the authorization to publish. The package name stays `nota-bene-ide`; the
   repository root remains private.
7. If the workflow cannot publish, do its steps by hand from a checkout of the tag, with
   `npm publish <archive> --access public --tag latest` and a confirmed `npm whoami`; never
   print credentials.
8. Verify registry version and integrity after publication.
9. Verify Codex marketplace installation from `main` in an isolated `CODEX_HOME`, then
   smoke-test the published npm runtime with the installed skill and a fake Codex backend.
10. Keep later repository-only plugin/documentation changes distinct from that archive.

Do not restart a live NB server as part of building or publishing.

## Access token

Nothing on the machine reaches the API or the socket without a secret (`server/src/auth.ts`). The server listens on 127.0.0.1 only, but any local process or other OS user could connect, so an unset `Origin` is accepted only with valid auth.

- The secret is `<NOTA_BENE_HOME>/token`, created on first need with an exclusive link (two first launches agree). **Only a missing file makes a token (the ssh rule)**: a loose mode (group/other readable), garbage content, a foreign owner, a directory, a FIFO or a symlink (opened with `O_NOFOLLOW|O_NONBLOCK`) make the server and every helper throw a clear message naming the file and the fix (`chmod 600 <file>`, or delete it to get a new token, which logs every window out). Nothing is rotated silently. A state folder owned by another user is refused. The same rule holds for `control-token`, which is made at server start, never by a request. The secret never goes in argv, in the environment of the agent or of `!` commands (the server reads the file), or in a log. The startup line, `/info` and `$TMPDIR/nota-bene-PORT.log` (created 600, `O_NOFOLLOW`) do not print it.
- Browser: the window is opened on `http://127.0.0.1:PORT/#t=<login>`, where `<login>` = HMAC(token, `nota-bene:login:<port>:<nonce>`): **never the raw token**, so a URL that leaked opens that one window and dies when its launcher exits (a URL from `--url` lasts until then; after a crash relaunch or a new launch it is dead). The page (`web/src/net/auth.ts`) takes the fragment out of the address bar first, then POSTs `{login}` to `/auth` (same-origin, JSON; the raw token is refused there) and gets `Set-Cookie: nb_<port>=<cookie credential>; HttpOnly; SameSite=Strict; Path=/; Max-Age=1 year` plus the page's **key** in the JSON body, which it keeps in localStorage (`nb.key`; origin-scoped, port included).
- Per-launch nonce: the launcher makes a random nonce and hands it to every server it starts (env `NOTA_BENE_NONCE`). **Exit 75 (the user's restart) keeps it, so open tabs stay logged in; a crash relaunch takes a new one and the launcher opens a fresh login page**, so whatever the crashed launch handed out is dead and the user is logged in again. An unsupervised server makes its own; `npm run dev` makes one for the whole session (`scripts/dev.mjs`), so a `node --watch` reload does not log the page out. It is public, not a secret, and still stripped from the server's own env after reading and from `shellEnv`. Every derived value is HMAC(token, `nota-bene:<label>:<port>:<nonce>`) with its own label (`cookie`, `key`, `helper`, `login`; `proof` adds the challenge): a value captured in one launch is dead in the next, and one captured for a port is dead on any other. Tabs of the old launch show the overlay. A second tab, a reload and `Restart the server` keep working.
- Two tiers. The cookie alone opens **only `GET`/`HEAD` of `/file`, `/attach/<id>` and `/voice/<id>`** (what `<img>`, `<video>`, `<audio>` and a 3D loader's textures load with no way to add a header; `cookieRoute` in `auth.ts`). `/model` is not among them: its loader is a `fetch`, so it goes through `apiFetch` and needs the key. **Every other route needs the key as well, `/info`, `/tree`, `/sessions`, `/complete`, `/system/*` and the socket included, and so does any route added later (key tier by default; `server/src/auth.test.ts` pins every route in a table).** The key travels as the header `x-nota-bene-key` through the one `apiFetch` helper in `web/src/net/auth.ts` (every `fetch` in `web/src` but `/file` and `/attach` uses it), and the socket offers it as the `nb.<key>` subprotocol, echoed by the server, never in the URL. Helpers send `Authorization: Bearer <helper credential>`; that and the raw token as Bearer (a script of the user's own) open everything. A cookie without the key gets 401 on the socket and everywhere but `/file` and `/attach`, with no frames; a page whose key is gone (cleared storage) gets the 401 from `/info` and shows the overlay.
- No derived value goes to a port that has not proved itself: **helpers first ask the public `GET /hello?c=<random hex, 16-64>`**, which answers only `{proof, n}` (proof = HMAC(token, `nota-bene:proof:<port>:<n>:<c>`) for the port the server is bound to; no root, no state; a malformed `c` is 400). `proveListener` / `verifiedBearer` (`auth.ts`) pick a fresh `c`, check the proof in constant time against the port they dialled, and only then derive the helper bearer from the `n` of the checked proof. A bad or missing proof means "not ours": nothing is sent, no retry. Every probe goes through it: `probeInfo` (`--find`, `--find --scan`, the launcher's liveness checks, `--detach`), `probeWindow` and the control relay (Settings → Windows), and `--url` / `--front`, which also refuse any URL whose listener did not prove itself, because the login URL carries the raw token in its fragment where the page's own script can read it. `--front http://localhost:N` / `--url http://localhost:N` are the dev page: the backend (4780) must prove itself directly and so must `localhost:N` through the Vite proxy (`/hello` is proxied; the proof is bound to 4780). A program that relays `/hello` to the real backend would still pass; that is what a proxy is, and it is dev only.
- Protected: every route and `/ws` (401; the socket is refused at the handshake, before any event; the socket server upgrades `/ws` only). Public: `/`, the static assets, `/auth` (POST, own-Origin only) and `/hello` (the proof, below). The Host and Origin checks stay in front: a non-GET request needs an Origin from the allowlist **even with a Bearer** (a script sets `Origin: http://127.0.0.1:PORT` itself; without one the answer is 403), and `/ws` accepts an unset Origin only with valid auth. `/control/` is the exception: its own token (`control-token`), and any Origin is refused. Compare in constant time.
- The launcher opens the browser on a mode-600 page in `<state>/open/` that redirects to the login URL (so the token is not in `ps`; the page stays until the next sweep, see the state list). `--detach`'s `opened URL` / `already-open URL` and `nota-bene --url PORT` carry the `#t=` fragment (the user's own terminal: a second browser can log in with it); the foreground `already open at` line, every log and **everything the `/nb` skill prints** do not — the skill's `NB: opened URL` / `already open at URL` are plain URLs, because its output enters the Claude Code transcript and goes to the API. A browser logs in through the redirect page: the launcher opens it for a new window, and `open.mjs` calls `--front` for one already open. Helpers: `nota-bene --url PORT` (the login URL), `--front PORT` (bring to front, logged in), `--find DIR --scan` (also asks the other ports of the range, which replaced the skill's bare `curl`). 
- A page without a login (a bookmark, a copied address, a tab of an earlier launch) shows the overlay "This window is not logged in" and stops reconnecting: a socket that closes before its first frame is checked with `GET /info` (with the key), and a 401 there ends the retries. A server restart (exit 75) and an open tab keep working (the nonce is kept).
- `startServer` takes the test-only `insecureNoAuth`; `main.ts` and the launcher never set it and there is no flag or env var for it. Unit tests that are not about auth pass it; `server/src/auth.test.ts` and `e2e/auth.spec.ts` run with auth on. The e2e servers are seeded with a known token and nonce (`e2e/serve.mjs`), and `e2e/playwright.config.ts` gives every project the matching cookie and localStorage key as its storage state (`e2e/auth.ts`).
- Trust limit: the token file is readable by the same OS user, so the user's own agent (and anything else running as that user) can read it. That is accepted: the aim is to keep out other users and other local software that cannot read the file, not the user's own tools. **File routes never serve the state folder**: `/file`, `/tree`, `/model`, `/complete` and every `src=` source (live worktrees and git blobs) refuse, list and search nothing whose real path is the state folder or inside it (`server/src/stateGuard.ts`), so a root that contains it (a session in `$HOME`) does not hand the token to a cookie. Residual risk, accepted for v1.0: browsers send cookies to every port on 127.0.0.1, so while a window is live a local web server the user visits sees its `nb_<port>` cookie, which reads files in the project through `/file` and pasted images through `/attach/<id>` (a GET of a pasted image id also restores it from the trash), nothing else, and cannot open the socket or write (the key is in localStorage, which no other origin reads); it is dead after the next launch. Rotating everything means deleting `<state>/token` and restarting the server: a window that is live under the old token can no longer be proved by the helpers, so it has to be reopened (`--find` does not see it, and a `/nb` or launch meanwhile starts a second window on the folder). A token that was ever committed to git stays readable through `.git/objects` even after the file is removed from the tree; the state folder is not a place for a repository, and the file guard (`stateGuard`) only covers the working tree and the branch reads.
- `/file` serves `.html` and the other text kinds as `text/plain` and everything under a CSP `sandbox` (opaque origin, so cross-site for cookies): a sandboxed document that loads a subresource from `/file?...` gets no cookie and so a 401. Only a top-level opened `.svg` with absolute `/file?` references is affected (the app never frames `/file`; `<img src="/file?...svg">` and media are same-origin loads and carry the cookie). The auth on `/file` was left alone.
- Dev: `npm run dev` has its own state dir and so its own token; `npm run dev:open` opens `http://localhost:5173` logged in (the Vite proxy forwards `/auth` and `/hello`, the cookie is `nb_4780`; it refuses to hand the token to a listener on 5173 that cannot prove itself). Upgrading: a window started before this version has no `/hello`, so the new helpers take it for dead (`--find` misses it, Settings → Windows lists it as silent) until it is relaunched.
- Smoke on 4790 (manual): with a temp `NOTA_BENE_HOME` the server creates `token` at start. Log a browser in with `node bin/nota-bene.mjs --front 4790` (or print the URL with `--url 4790`), both with the same `NOTA_BENE_HOME`: they ask the window for its proof first. For the API use the raw token as a Bearer in your own shell: `curl -H "Authorization: Bearer $(cat "$NOTA_BENE_HOME/token")" http://127.0.0.1:4790/info`. Without a credential every route but `/`, `/auth` and `/hello` answers 401.

- Remote connector (`nota-bene remote`, `server/src/remote/`): reads each provider's `token` (never creates one) and sends the helper bearer only to a window that answered `/hello` with that token; adds `Host: 127.0.0.1:<port>`, and `Origin` on non-GET, to what it proxies; refuses `/control/*`. Its own secrets are `<NOTA_BENE_HOME>/remote/host.key` and `devices.json` (mode 600, `readPrivateFile`'s checks); its only listener is `remote/control.sock` (mode 600; on Windows the named pipe `\\.\pipe\nota-bene-remote-<hash>`, whose clients prove `remote/control-secret`). Tests (`server/src/remote/*.test.ts`) build and run the real relay with `go`, so `go` must be on PATH for `npm test`.

Enter / Run sends the client message `shell-run {id, cmd}` (owner socket only, the same validation as every client message: `cmd` a non-empty string of at most 32 KB; no HTTP route). A refusal (one is running; a switch is in progress) is the event `shell-refused {id, reason}` to the asking socket, and the page puts the draft back. The server (`server/src/session/shell.ts`) runs `$SHELL -lc -- cmd` in the current root (`$SHELL` only when its basename is sh, bash, zsh, dash or ksh, else `/bin/sh`: a fish user gets `/bin/sh` for `!`, because `-lc --` is untested there; the `--` keeps `! --version` a command), stdin `/dev/null`, in its own process group. One command at a time per window; it works while the agent is busy and starts no turn. The feed gets one block: `shell-start` (stored; kept through a compaction while the run goes), `shell-out` (live only; the WHOLE tail so far, ANSI stripped, stdout and stderr merged, replacing what the page shows, at most ten a second and skipped for a socket more than 1 MB behind, so a command that prints without end cannot grow the server; the pipe is always drained; a socket that attaches mid-run gets the tail in one frame), `shell-end` (stored; the last 64 K characters, `truncated`, exit code, `stop` = `user` | `timeout`, `error` when it could not start). `shell-stop {id}` sends TERM to the group, KILL after 3 s (the KILL still comes after the block has ended); the same after 10 minutes (`stop: 'timeout'`). When the shell exits, the rest of its group gets TERM and, 3 s later, KILL (polled every 150 ms: an empty group is not signalled again, its id may be reused; the run stays in the exit hook until then): a background job (`cmd &`) ends with the command. A session switch, a restart, a `/clear` and a server close stop a run quietly (no end event, its output dropped). A process exit hook kills the live group on any normal exit, and `main.ts` turns SIGINT, SIGTERM, SIGHUP and SIGQUIT into a close; only a SIGKILL of the server itself leaves a running command behind (no watcher process). No pty: an interactive command (an editor, a pager, a password prompt) gets EOF and ends on its own, usually with a non-zero code; the block shows no hint. On Windows the shell is the `shell` preference (`auto`: Git Bash, else `pwsh`, else Windows PowerShell 5.1; the WSL bash never): Git Bash `-lc -- cmd`, PowerShell `-NoLogo -NoProfile -NonInteractive -Command cmd`, `cmd /d /s /c "cmd"` one line only; not detached, hidden windows, stdin closed, the same `shellEnv` plus `NOTA_BENE_SHELL_RUN=<mark>` on a Git Bash run. A chosen shell that is not installed ends the run with `shell-end.error` `shell-missing:<shell>` (worded by the page). The first output line names the shell (`[Git Bash]`) and a non-bash run adds `[run in <shell>]` at the end of the agent's `bash-stderr`. Stop, the timeout and a close kill at once (a Git Bash run through MSYS by its mark, background jobs included; other shells as a `taskkill` tree); a background process of a PowerShell or cmd run that outlives the shell is not tracked. Output is decoded per chunk (UTF-8, else the OEM code page).
The agent hears of finished runs with its next message, no extra turn: at the moment the text is handed to the agent the server puts them in front of it in Claude Code's own form (checked against its transcripts: `<bash-input>cmd</bash-input>`, then `<bash-stdout>…</bash-stdout><bash-stderr>…</bash-stderr>`; a silent run is `(Bash completed with no output)`; stdout and stderr stay separate, 32 K characters each, a cut marked; `</bash-` in a command or its output is written `<\/bash-` so output cannot close a tag; a stopped run or a non-zero exit adds a line to stderr; the whole lead is at most 64 K characters, the oldest runs left out with a note after the blocks (a replay drops it), the newest always in; at most 10 runs wait). A failed hand-over puts the runs back (not for a `/clear`: they are dropped as it is accepted, a failure there loses them). A message that is a slash command (`/compact`, `/clear`, a skill) goes out as is and the runs wait for the next one (a `/clear` drops them when it is handed over, so the message behind it starts clean). The queue survives the agent's in-process restart, and is dropped on a switch to another session and on a `/clear`. The feed shows the message as typed, without the blocks; on a transcript replay the exact leading blocks of a user message (also one with images) become shell blocks again (no exit code kept; text a user typed in exactly that form at the start of a message would show as a block too: accepted). The block lives in the hub like other events, so a page reload replays it; a block of a run the agent never heard of (no message since) is lost with a server restart or a ↻, because the transcript holds only what went to the agent.

One tab per window: the first socket owns the session; a second tab gets "Окно уже открыто в другой вкладке" and can take over ("Работать здесь"), after which the old tab gets close code 4001 and shows the overlay too. A reload of the owner within 700 ms is not a second tab. Tests that need several sockets pass `oneTab: false` to `startServer`.

Session switch and ↻ are in-process: the server closes the SDK query and resumes (another) session, possibly re-rooting to another project folder; a new session may only start in the current root or in a folder that already has sessions.

Restart semantics: ↻ restarts the agent, not the server process; it stays available while the agent is busy (escape hatch). The ↻ menu also has "Restart the server", shown only when `/info.supervised` is true (the window runs under the launcher): the server exits with code 75 and the launcher relaunches it with `--continue`, so the session resumes. Under `npm start` / `npm run dev` there is no such item. ⏻ in the header (Stop window) POSTs `/stop`: the server exits 0, which a launcher takes as stop (it unregisters the window and exits); the tab parks on the `stopped` connection state and never reconnects.

Smoke hygiene (manual run with the real agent): restart the server before reloading the page (a new page against an old server is the reverse version skew); use a temp `NOTA_BENE_HOME`, a temp `CLAUDE_JOURNAL_VAULT` (or the agent in the temp project follows the global journal protocol and writes into the real vault) on port 4790. Afterwards move the temp projects' transcripts (`~/.claude/projects/-private-tmp-nb-*`) to the Trash, or they clutter the session picker.

## Audit log

When a window misbehaved (a stopped turn, a lost connection, a crash loop), read its audit log before guessing: `<NOTA_BENE_HOME>/audit/YYYY-MM-DD.jsonl` (UTC days), one JSON object per line with `ts` (ISO, UTC), `port`, `pid`, `ev` and the event's fields. `ev` is `server-start` (`root`, `agent`, `node`, `supervised`), `server-stop`, `server-exit` (`code`: 75 is the user's restart), `ws-open` / `ws-close` (`conn`, `code`; 4001 is a takeover), `client` (what the page asked: `type` is the client message type, `conn` the socket; `send` has `chars`, `force`, `comments`, `images`), `event` (what the server told the page: `kind` as in the protocol, `turn-end` has `stop` and `secs`, `tool-call` has `tool`) and `agent-system` (an SDK system message the chat does not show: `subtype`, retry numbers, a short `error`). A turn that ended `interrupted` was stopped by a `client` `interrupt` (the stop button), a `send` with `force`, or a `restart` just before it. Text is never there, so quote what you find freely.

## Whisper host

Dictation and voice messages run Whisper in one background process per state folder, not one model per window: the **Whisper host**. A window starts it on its first transcription (any window of Claude, Codex or omp: the install is per state folder, so the host is too) and every window of that folder sends it jobs. Code: `server/src/dictation/hostWire.ts` (framing, messages, caps, deadlines, paths), `hostMain.ts` (the host: socket server, queue, idle clock), `hostEntry.ts` (the process entry; bundled as `host.js`), `hostClient.ts` (the window's side), `transcribe.ts` (delegates to the client; `transcribeLocal` is the in-process fallback), `pipelineHost.ts` and `pipelineWorker.mjs` (the model thread, which the host reuses unchanged).

- **Where.** `<NOTA_BENE_HOME>/whisper-host/` (mode 700, owner checked before use), outside `whisper/` so that Remove, which deletes that folder, does not delete a socket that is still answering. In it: the socket `h<HOST_PROTO>-<sha8 of the pins>.sock` (600; a host of another protocol or other pins gets its own name, so incompatible windows never share one), `host.log` (the host's stdout and stderr, 600, this start's only) and `host.log.1` (the start before it, which keeps the cause of a failed start), `spawn.lock` (taken by the window that starts a host so that windows that find nobody together start one; a lock older than the longest a live holder keeps it, 25 s, is nobody's whatever its pid says, and is taken over) and, briefly, `.xxxxxxxx.sock` (a host binds under that name and renames it; a leftover of one killed in between is swept by the next start unless something still answers on it). The socket path must fit `sun_path` (about 104 bytes), so a long `NOTA_BENE_HOME` is a fallback to the window's own model, told once. **Windows** has no unix sockets: the host listens on the named pipe `\\.\pipe\nota-bene-whisper-<16 hex of SHA-256 of the real state base path>-h<HOST_PROTO>-<pins>`, and windows and host prove `whisper-host/host-secret` (made once, read with `readPrivateFile`) to each other in `hello`; the folder holds `host-secret`, `spawn.lock` and the logs, no socket file. Find your own host by the pipe name, not by a file. A host secret that is not valid sends the window to its own model, told once.
- **The model's files.** The installer's load (`openPipeline(dir, { download: true })`) is the only one that goes by the model id and the pinned revision and may fetch the model, into `<whisper>/models/<model>/<revision>/`. Every other load (a window's, the host's) reads that folder by its path with `env.allowRemoteModels = false`: transformers.js downloads what its cache lacks unless told not to, and a load that races a Remove must fail, not fetch ~430 MB again into the folder being deleted. By id it would not even work offline: the library probes which files the pipeline needs without the revision, looks for `preprocessor_config.json` at `main`, and loads a pipeline with no processor (every job fails on a null `feature_extractor`). So the installer ends with the same load, by path and offline, before it writes `ready.json`: a download that does not load is a failed install, not a failure of every job later (`verifyModel`; a test's own `fetchModel` skips the real check).
- **Lifetime.** Detached from every window, so it survives window stops, restarts (exit 75) and updates (an update restarts the window servers and leaves a running host as it is until it idles out; a version with another protocol or other pins finds its own socket name, so briefly two hosts may run). **Lazy load:** the model loads at the first job; `hello` and `status` say `loaded: false` until then, which is a healthy host. **Idle exit:** after `WHISPER_IDLE_MS` (10 minutes) with nothing queued or running the host exits 0, which unloads the model. The clock counts jobs, not connections: a window that leaves, or a `status` question, does not postpone it. A window closes its own connection after 60 s without a job (`IDLE_CLOSE_MS`), so an idle host has no peers.
- **Queue.** One job runs at a time, the windows take turns (round-robin), so a long voice message in one window does not starve another's dictation. Limits: 16 queued per window, 64 in all and 64 MiB of audio, then the answer is `busy` (HTTP 503 `{error: 'busy'}`, a voice message `failed`); 32 windows at most, the next one is told `full` and uses its own model without it counting as a failure of the host. A job is Int16 PCM in a frame of at most `MAX_AUDIO` plus a header; the host takes audio and nothing else (never a path or an attachment id) and never reads preferences: the window checks `whisperOn()` before it sends.
- **Deadlines.** A model call has `max(2 min, 10 x the audio's length)`; past it that job is answered `failed` and the host exits (the other windows see a plain disconnect and retry once on a fresh host). The model load has 5 minutes. A window waits `clientDeadlineMs` (the load, the call and 30 s) before it takes a silent host for dead, 5 s for `hello`, 10 s for a host it started to come up. The window's own in-process fallback has no deadline: a model call that hangs there wedges that window's transcription queue, as it always did.
- **Fallback to the window's own model** (`transcribeLocal`, the model in this process). Silently: no `host.js` beside the bundle (`hostEntryFile()`), a job over one frame, a host that is `full`. Told (`reportError`): a socket path that does not fit and a host folder that belongs to someone else (once each), and three deaths or failed starts within 60 s (each time it happens), after which the window stays on its own model for 5 minutes. A window starts a host, and loads its own model, only for an install that reads as ready (`whisperPhase()`, checked right before the spawn with nothing awaited between): otherwise the job fails as Whisper off, not counted as a failed start. A job that has lost a host under its one retry fails (`HostLost`) instead of running in the window: whatever killed the host may be the clip, and a native crash there would take the window with it. A `failed` answer (the model said no) is the job's error: it is not retried and the host is not blamed. A test's own `load` never goes near the host.
- **Remove.** `POST /dictation/remove` goes in this order. (1) Whisper is off and the install no longer reads as ready (`withdrawWhisper()` deletes `ready.json`; the preference goes to off): a dictation that passed its gate before, or a job that retries after the host is stopped, then finds Whisper off (HTTP 503 `dictation is off`) instead of starting a host from files that are about to go. An install in progress is refused (409) before anything is touched. (2) The host for these pins stops: `shutdown {reason: 'removed'}` (jobs still queued fail `off`), on the window's own connection to it when it has one. (3) Waits up to 5 s for that connection to end. A host that still holds it after that ignored the shutdown and is SIGTERMed (on Windows `killTree`) by the pid it answered `hello` with on that very connection: the live peer, never another process, this process or a group; the socket name decides nothing. If the connection ended but the socket name still answers (a new host took it), that host is asked once on a fresh connection by the same rule, and no third. SIGKILL is not sent. (4) The window's own model is reset and `whisper/` is deleted. With no host running steps 2 and 3 do nothing; a host that cannot be reached is reported and the removal goes on. Other windows connected at that moment see the close as one death (three within a minute are needed to send them to their own model).
- **Status.** `GET /dictation` carries `host: {loaded, queued, running} | null` (null: no host, a full one, one that does not answer within 2 s, one of another protocol; it never starts a host and never fails the request). It is a short connection of its own, never the window's: asked on that one, a page that polls would keep it open until the host's idle exit closed it. For a look from a shell: `curl -H "Authorization: Bearer $(cat "${NOTA_BENE_HOME:-$HOME/.nota-bene}/token")" http://127.0.0.1:<port>/dictation` (a Codex or omp window keeps its token in `<base>/providers/<provider>/token`, and its preferences there too), `pgrep -fl hostEntry.ts` (a checkout) or `pgrep -fl host.js` (the package), and `tail <NOTA_BENE_HOME>/whisper-host/host.log`. There is no Settings display of it yet (a string there needs all six languages).
- **Stopping it safely.** Remove Whisper in Settings does it for the user. By hand, only a host of your own temporary `NOTA_BENE_HOME`: SIGTERM its pid (it unlinks its socket, fails its jobs and exits; on Windows there is no SIGTERM: `taskkill /T /F /PID <pid>`). The host under the user's real `~/.nota-bene` serves their windows: an agent run that does not own it leaves it alone and reports it. It stops itself 10 minutes after the last job anyway.
- **Package.** `scripts/build-package.mjs` bundles `hostEntry.ts` to `server/src/host.js`, beside `server/src/main.js` where `hostEntryFile()` looks; `dictationAssetDir()` finds `pipelineWorker.mjs` and `npm-shrinkwrap.json` in `server/src/dictation/` from either bundle. `bin/package.test.ts` runs the built `host.js` (starts, publishes its socket, idles out) and sends it a job with a stub model. The host's environment is `PATH`, `HOME`, `TMPDIR`, `NOTA_BENE_HOME` and `NOTA_BENE_TEST_WHISPER_IDLE_MS` only (on Windows also `SystemRoot`, `windir`, `USERPROFILE`, `TEMP`, `TMP`, `LOCALAPPDATA` and `APPDATA`): it never sees a window's token or nonce, and it has no TCP listener (a 600 socket in a 700 folder, or on Windows a pipe whose clients prove `host-secret`, is the same same-user boundary as `token`; pages, phones and the remote connector cannot reach it).
- **Tests and smoke.** `NOTA_BENE_TEST_WHISPER_IDLE_MS` (milliseconds, above 0) replaces the 10-minute idle time, for tests and smoke runs only. `hostMain.test.ts` drives the host with a fake worker factory; `hostClient.test.ts` runs real hosts (`hostEntry.ts` with a stub package in place of transformers.js) on unix sockets in `/tmp/nbw-` folders, which fit `sun_path` where `os.tmpdir()` on macOS does not. Every test file of the node project starts with a state home of its own (`vitest.node-setup.ts`: `<tmpdir>/nb-test-home-<random>`, named, not made, removed after the file), so a test that forgets to set `NOTA_BENE_HOME` cannot reach the real `~/.nota-bene` (a host once ran there with the real model, started by a test); a test that needs a host sets a short home of its own, restores the file's home in `afterEach`, kills every process it started and bounds every wait. After a run, `pgrep -fl hostEntry.ts` and `pgrep -fl host.js` must show none of yours.

## You may be running inside this tool

If the project root is this directory, the chat window you are talking through is most likely served by the rebuild (root).

Rebuild window:

- Changes to `web/` take effect after `npm run build -w web` and a page reload (tell the user to reload). "Restart the server" (exit 75) rebuilds a stale `web/dist` before the server starts again (the same stamp check as at launch: nothing stale, no build), so a restart over stale web sources is down for the build time; a manual `npm run build -w web` first is optional. A crash relaunch never builds. A failed build is logged, the old `web/dist` is served, and the build is not retried until a source changes. While the launcher builds, its registry entry carries `building`, so another launch on that folder keeps waiting instead of opening a second window. Tests move the build with `NOTA_BENE_BUILD_ROOT` (next to `NOTA_BENE_BUILD_CMD`; the build lock is named after that tree), so they never touch the checkout's `web/dist`.
- Changes to `server/` (or `shared/`) need a server restart: ask the user to open the ▾ menu next to "↻ Agent" and pick "Restart the server"; the session resumes automatically. **Do not kill, restart or curl your own window's server** — that kills your own turn. Finish the turn first.
- Before asking for "Restart the server", check the edit: run `npx tsc -b`, then start the server once on 4790 with a temp project and temp `NOTA_BENE_HOME` (`node server/src/main.ts <tmpdir> --port 4790`), see it answer `/info` (it needs the token: `curl -H "Authorization: Bearer $(cat <tmp home>/token)"`, see Access token), and stop it. A broken server edit crash-loops under the launcher, which gives up after 5 crashes — the window does not come back and the user has to relaunch it.
- Opening a second browser tab on your own window (a manual check, say) is parked behind the "already open" overlay, and clicking "Работать здесь" there parks the user's tab (4001); check on a separate 4790 window instead.
- After a server/shared edit the window shows a "Restart server · code updated" button (`/info.codeChanged`, supervised windows only); still run the pre-check above before asking the user to press it.
- Test server changes on a separate port (4790) with a temp project dir and temp `NOTA_BENE_HOME`, never on a live window's port.
